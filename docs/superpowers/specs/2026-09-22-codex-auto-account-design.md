# codex-sub-agent 账号自动分配

## 目标

调用方不再需要知道哪个账号还有额度。`--account auto` 让工具自己挑，撞上额度上限就换下一个。

用户原话：「我希望调用这个 skill 的时候，不再有管理账号的麻烦，直接调用就好了。我们这边根据账户的
额度和重置时间，来决定怎么分配账号。」

## 一、可观测性决定了方案的形状

设计前先测了一轮，结论决定了后面所有选择：

| 事实 | 可观测吗 | 怎么测的 |
|---|---|---|
| 账号**还剩多少**额度 | **不可以** | 没有 `codex usage`/`quota`/`limits`/`account` 子命令；`codex doctor` 不报；`auth.json` 里没有 |
| 账号**已经用完了** | **可以**，且消息自带恢复时间 | 24 份会话文件里有 `You’ve hit your usage limit … try again at Sep 25th, 2026 5:04 PM` |

所以「根据额度分配」在字面意义上做不到——**没人能在用之前知道还剩多少**。
能做的只有：**试了才知道；撞上了把恢复时间记下来；下次用它排顺序。**

配套测到的两件事，直接约束了设计：

1. **额度是周级的，不是小时级。** 2026-09-22 实测：`acct3` 恢复于 9/25 17:04，`default` 恢复于
   9/26 17:47，都在 3~4 天后。一次撞上限，那个账号停好几天——这让「每次 run 都从头试一遍」的
   无状态方案代价过高（3~4 天里每次都白烧前面那几次启动）。
2. **三个账号的恢复时间是错开的。** 所以有意义的排序键是恢复时间本身，不是套餐档位
   （`default`=pro、`acct2`=pro、`acct3`=plus）。先烧大的还是先烧小的，一周总容量不变，
   两种说法对称且都无法测量——按奥卡姆剃刀，档位不进排序规则。

## 二、地基：`USAGE_LIMIT_MARK` 从来没匹配过

`judge()` 里早就有撞上限的特判，但它是**死代码**：

```
源码常量：USAGE_LIMIT_MARK = "You've hit your usage limit"   ← ASCII 直引号 U+0027
日志实际：              You’ve hit your usage limit         ← 弯引号 U+2019
```

后果当场可见：`status` 把三个撞上限的任务全报成「报告缺失或为空＝没正常收尾」，
而不是「撞上账号额度上限，换账号或等额度恢复」。这与本会话修过的 `^ERROR:` 大小写 bug
是同一类——**字面量对不上现实，于是静默给出一个「更差但看着合理」的答案**。

### 测试为什么没发现

`test_codex_sub_agent.py:107` 的 fixture 注释写着「真实日志片段（2026-09-19 从
`~/.claude/jobs/2e6058df/tmp/codex-*.log` 取）」，但它里面是**直引号**——抄的过程中被
规范化了。于是 fixture 和常量用同一个错字符，两条测试永远绿。

这是模块头那份空测试清单里**没有的第十种**：
**号称抄自现实、抄的时候字节被悄悄改了。** 要补进那份清单。

### 修法

**不是**把直引号换成弯引号——那仍然押在一个会变的字符上。
**把判据缩短到不含任何标点的那一段**：

```python
USAGE_LIMIT_MARK = "hit your usage limit"
```

一个字符都不用归一化，codex 以后怎么改引号都打不着它。
只在「报告缺失」这一支里被查，误报面本来就窄，和原常量一致。

配套测试测的是**性质**而非字节：直引号版本和弯引号版本**都**必须判成撞额度上限。

## 三、状态：每个隔离目录一个 `usage_limit.json`

```json
{"reset_at": "2026-09-25T17:04:00", "raw": "Sep 25th, 2026 5:04 PM"}
```

| 决定 | 理由 |
|---|---|
| 放隔离目录（`~/.codex-subagent[-<账号>]/`） | 限流是**账号**的属性，而账号已经有一个家。`ensure_isolation` 只要求子目录存在、`config.toml` 是普通文件、`auth.json` 是软链，**不拒绝多余文件**，放这里合法 |
| 留 `raw` | 审计线索。解析错了（时区、格式变更）一眼看得出，不用回去翻日志 |
| **不**留 `seen_at` | 没有消费者。唯一的读者是排序，排序只看 `reset_at` |
| **不**做过期清理 | 时间一过，它自然排到最前面。自清理，不需要额外机制 |
| 解析失败 → **不写文件** | 宁可没有记录（退化成无状态、排最前、照样会被试），也不要写一个假时间进去 |

### 时区：不编造

消息里没有时区，实测也推不出来（恢复时间在 3~4 天后，没法拿文件 mtime 反推）。
**存朴素本地时间，不给它安一个我们不知道的时区。**

这样做安全，是因为下一节那条约束：这个值**只当排序键**。误差 ±12h 只在两个账号的恢复时间
相差 12h 以内时才改变顺序，代价是多一次 codex 启动。**有界且良性。**

## 四、分配：状态只排顺序，不准拒绝

这是本设计最重要的一条约束，其他都为它服务。

> **「全部账号都满了」这个结论，永远来自真实尝试，不来自文件。**

状态文件写错（时区、时钟偏移、OpenAI 改文案）时，最坏后果被钉死在**顺序排差、多一次启动**，
而不是「把一个好账号误判成死的、还告诉调用方没号可用」。后者正是这个工具反复在修的那类谎。

### `--account auto`

```
候选 = account_choices()                       # default / acct2 / acct3，扫 ~/.codex-accounts 得到
排序键 = (该账号的 reset_at, 账号名)            # 无记录 → datetime.min，排最前
                                               # 账号名做第二键，保证顺序确定，不随扫描顺序漂
已存在的任务名 → 它的账号排最前                 # 沿用，但仍可被重试搬走

for 账号 in 排好序的候选:
    跑一轮
    if 判据 == 撞上额度上限:
        ① 从日志里解析 reset_at，写该账号的 usage_limit.json
        ② 删掉本任务在该 home 的元数据          ← 见下
        continue
    return 本轮结果                             # 不管成功还是别的失败，都到此为止

全部撞上限 → failed，reason 逐个列出每个账号的恢复时间
```

**第 ② 步是必须的，不是清理癖。** `cmd_run` 有一道护栏：同名任务不许跨账号
（注释原话：「那会让同一个名字出现在两个隔离目录里，另一份成了再也够不着的孤儿元数据」）。
而 `run_codex` 在开跑**之前**就把元数据写进了该账号的 home。不删，第二次尝试会被自己的护栏挡住。
删掉后不变量恢复：**一个任务名在任何时刻只属于一个隔离目录。**

日志**不删**：它是撞上限的证据，而恢复时间已经提取进 `usage_limit.json`，日志本身是冗余的。
下次同名任务跑在这个账号上时 `run_codex` 追加写，`read_round` 按字节偏移切本轮，不会被旧内容污染。

尝试次数上界 = 账号数（当前 3）。没有循环。

### 四处容易读歧义的地方，写死

| 问题 | 答案 |
|---|---|
| 重试用同一份 brief / effort / skills 吗 | 是。只有账号变，其余逐字不变 |
| 「撞上额度上限」谁判的 | **复用 `judge()`**，不另写一套检测。两处判据会漂移，这正是本工具反复在修的那类 bug |
| 「任务还在跑」的护栏查几次 | **一次**，进循环之前。它问的是「这个任务名此刻有没有活着的 codex」，与试哪个账号无关 |
| `ensure_isolation` 呢 | **每次尝试都跑**，对当次那个账号。它建目录、接 `auth.json` 软链，是那个账号能开跑的前提 |

### 为什么跨账号同名护栏不用改

`cmd_run` 现有那道检查（任务名已存在且不在本账号的 home → 拒跑）在 auto 模式下**自动满足**：

- 第一次尝试：已存在的任务名其账号排最前，所以 `old_home == home`，通过
- 重试时：上一个账号的元数据**已经在第 ② 步删掉了**，`find_meta` 返回空，无从撞车

护栏一行不改，不变量靠删元数据维持：**一个任务名在任何时刻只属于一个隔离目录。**

### `--account <具体账号>`

只试这一个，**不重试**。但撞上限**照样写** `usage_limit.json`——
**这是关于账号的事实，与调用方式无关。** 强制模式踩到的坑，应该让 auto 模式变聪明。

跨账号同名任务的护栏在强制模式下**原样保留**。

### `--account` 仍然必填

取值多一个 `auto`。字面遵守「不要用默认缺省值」：没有任何隐式选中的值。
代价是每次调用都要写一遍 `--account auto`，用户已知情并选择了这个。

## 五、刻意不做

| 不做 | 理由 |
|---|---|
| `status` 增加账号限流行 | 「什么时候能干活」的答案放在失败信息里，那正是需要它的时刻。而 `status` 的机器可读格式是刻意设计过的契约，不为一个次要信息破坏它 |
| 新增状态码 | 沿用 `judge` 的既有规矩：「两种特判只改 reason、不新增状态」。全部账号满了仍是 `failed`，只是 reason 更具体 |
| 按套餐档位排序 | 见第一节：对称且不可测量的偏好，属于该被剃掉的实体 |
| 预测/跟踪剩余额度 | 不可观测。任何基于它的设计都是在猜 |

## 验收判据

1. 常量不含任何标点；直引号与弯引号两个版本都判成撞额度上限；用现网真实日志字节跑 `judge`，
   `state=failed` 且 reason 含「额度」
2. `usage_limit.json` 含且仅含 `reset_at`、`raw`；畸形输入不崩、不写文件、不影响本轮判据
3. `--account` 仍必填且取值含 `auto`；排序键是 `(reset_at, 账号名)`；撞上限后删元数据再试下一个；
   尝试上界 = 账号数；全满时 reason 逐个列出恢复时间；已存在的任务名其账号排最前
4. 强制模式撞上限写 `usage_limit.json` 且只启动一次 codex
5. `SKILL.md` / `README.md` 与实际 CLI 一致
6. `python3 -m unittest test_codex_sub_agent` 全绿，测试数不少于 250（只增不减）
