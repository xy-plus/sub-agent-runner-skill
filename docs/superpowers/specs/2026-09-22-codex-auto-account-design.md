# codex-sub-agent 账号自动分配

## 目标

调用方不再需要知道哪个账号还有额度。`--account auto` 让工具自己挑，撞上额度上限就换下一个。

用户原话：「我希望调用这个 skill 的时候，不再有管理账号的麻烦，直接调用就好了。我们这边根据账户的
额度和重置时间，来决定怎么分配账号。」

> **v2（2026-09-22）**：第一版被审查子代理退回。它证伪了两条我写的断言，并指出一个根因级问题：
> 这次改动把一条**给人看的解释性判据**升级成了**删状态、重跑任务的控制依据**，却没有同步提高
> 证据的可靠性。第二节的修法因此从「缩短字符串」改成了「限定证据来源」。

## 一、可观测性决定了方案的形状

| 事实 | 可观测吗 | 怎么测的 |
|---|---|---|
| 账号**还剩多少**额度 | **当前验证过的接口都不提供** | 没有 `codex usage`/`quota`/`limits`/`account` 子命令；`codex doctor` 不报；`auth.json` 里没有 |
| 账号**已经用完了** | **可以**，且消息自带恢复时间 | 24 份会话文件里有 `You’ve hit your usage limit … try again at Sep 25th, 2026 5:04 PM` |

所以只能做：**试了才知道；撞上了把恢复时间记下来；下次用它排顺序。**

配套测到的两件事约束了设计：

1. **额度是周级的，不是小时级。** 2026-09-22 实测：`acct3` 恢复于 9/25 17:04，`default` 恢复于
   9/26 17:47，都在 3~4 天后。一次撞上限那个账号停好几天——「每次 run 都从头试一遍」的无状态
   方案在这个量级下代价过高。
2. **三个账号的恢复时间是错开的。** 所以排序键是恢复时间本身，不是套餐档位
   （`default`=pro、`acct2`=pro、`acct3`=plus）。先烧大的还是先烧小的，一周总容量不变，
   两种说法对称且都无法测量——按奥卡姆剃刀，档位不进排序规则。

## 二、地基：额度判据现在既匹配不上真的，又匹配得上假的

### 匹配不上真的

```
源码常量：USAGE_LIMIT_MARK = "You've hit your usage limit"   ← ASCII 直引号 U+0027
日志实际：              You’ve hit your usage limit         ← 弯引号 U+2019
```

全量核对：**27 份日志、54 行额度错误，全部是弯引号**。后果当场可见——`status` 把撞上限的任务
报成「报告缺失或为空＝没正常收尾」，而不是「撞上账号额度上限」。

### 匹配得上假的（这条更严重，也是本节的根因）

现有判据是 `USAGE_LIMIT_MARK in round_text`——**对整轮自由文本做裸子串匹配**。
而同一份源码在 `_ERR_*` 那组正则上方自己写着：

> 日志里还混着 brief 原文和 codex 转述的子进程输出（cargo 的 `error[E0599]`、pytest 的
> `E   KeyError`、markdown 的 `## Warning Signs`），**所以绝不能用裸 grep ERROR —— 会大面积误报**。

额度判据正好违反了它自己定的这条规矩。审查子代理复现了：给 `judge()` 喂「brief 里提到
`hit your usage limit`＋真实的打断标记」，输出是

```
failed  撞上账号额度上限，换账号或等额度恢复
```

**本该是 `interrupted`。** 在第一版设计下，这个误判会进一步导致**删掉元数据、换账号重跑整个任务**
——原来只是解释错了，现在升级成了行为错。

### 修法：限定证据来源，而不是缩短字符串

两件事都要做，缺一不可：

| 改什么 | 为什么 |
|---|---|
| 判据缩短成 `"hit your usage limit"` | **砍掉含标点的那一截。** 剩下全是字母和空格，没有可变的地方——不是把直引号换成弯引号，那仍然押在一个会变的字符上 |
| **只在 `runtime_error_lines()` 的返回值里找它** | 那是已经按 `^ERROR:` / tracing target / `^Error:` 分类、并滤掉良性 target 的错误行。brief 原文、源码引用、子进程输出都进不了这个集合。**这是根因的修法**——判据建在已分类的事实上，不建在自由文本上 |

代价：`cmd_run` 要为重试判断多跑一次 `runtime_error_lines`（`judge` 内部已经跑过一次）。
实测 0.83MB 日志约 7.6ms，而 `run` 本身是分钟级的。**不为省这 8ms 去给 `Verdict` 加字段**：
加字段要改 7 个构造点，churn 和出错面都比多一次正则扫描大。
两个调用方共用**同一个谓词函数**，所以「两处判据漂移」在结构上不可能发生。

### 测试为什么没挡住

`test_codex_sub_agent.py:107` 的 fixture 注释写着「真实日志片段，2026-09-19 从
`~/.claude/jobs/2e6058df/tmp/codex-*.log` 取」，但它用的是**直引号**，而现存全部日志用的是弯引号。
那个目录已经不存在，**所以「是抄写时被规范化的」无法证实，也无法证伪**——不写进结论。

「两条测试永远绿」这个说法也要收紧。审查做了突变：把匹配逻辑整个禁掉，两条测试都会红。
所以它们不是什么都不测。**精确的说法是：测试和被测代码共享同一个错误假设，
于是它们对「判据与现实之间的偏差」完全不敏感**——改引号字符这个突变，测试照样绿。

这是模块头那份空测试清单（当前编号 1~7）里没有的**第 8 种**：
**fixture 与被测常量共享同一个未经现实核对的假设。**
防法不是多写几条断言，而是**让断言测「性质」并引入未经我手的真实字节**。

## 三、状态：每个隔离目录一个 `usage_limit.json`

```json
{"reset_at": "2026-09-25T17:04:00", "raw": "Sep 25th, 2026 5:04 PM"}
```

| 决定 | 理由 |
|---|---|
| 放隔离目录（`~/.codex-subagent[-<账号>]/`） | 限流是**账号**的属性，而账号已经有一个家。`ensure_isolation` 的不变量是：五个子目录存在、共享扫描根 `~/.agents/skills` 为空、`config.toml` 不是软链、`auth.json` 软链到该账号——**不枚举也不拒绝顶层多余文件**（实测放一个文件进去，再跑一次不拒且文件保留） |
| 留 `raw` | 审计线索。解析错了（时区、格式变更）一眼看得出，不用回去翻日志 |
| **不**留 `seen_at` | 没有消费者。唯一的读者是排序，排序只看 `reset_at` |
| 临时文件名**带 pid** | 这个文件是**账号级、跨任务共享**的，同一账号上的两个任务可能同时撞上限同时写。`write_meta` 用固定临时名是安全的，因为那里一个任务只可能有一个写者——**这个前提在这里不成立**，照搬会让两个并发写者把同一个临时文件写成混合内容，再原子替换进去 |
| 读失败一律当「没有记录」 | 文件缺失、坏 JSON、缺键、类型不对、时间串解析不了，全部返回 `None`。`None` 的含义是「无记录＝排最前＝照样会被试到」，那是安全的一边。反过来（读不出来就认定还在限流）会把可用账号锁死且调用方看不出原因 |
| 写失败不阻断执行 | 记录是优化，不是前提。写不进去最多让下次排序差一点 |
| 不做过期清理 | 见下 |

**不做过期清理的理由（第一版写错了，这里是改正的）：** 第一版说「时间一过它自然排到最前面，
自清理」——**这是错的**，排序根本不读当前时间，一条过期记录永远排在「无记录」（`datetime.min`）
之后。正确的理由是：过期记录排进「恢复得早的那一批」，批内按恢复先后排，语义依然正确；
而清理需要读当前时钟、需要判断「多久算过期」，是纯增实体。

### 时区：不编造

消息里没有时区，实测也推不出来（恢复时间在 3~4 天后，拿文件 mtime 反推不出来）。
**存朴素本地时间，不给它安一个我们不知道的时区。** 安全性来自下一节：这个值只当排序键。

## 四、分配

### 状态只排顺序，不准拒绝

> **「全部账号都撞上额度上限」这个结论，永远来自真实尝试，不来自文件。**

状态文件写错（时区、时钟偏移、OpenAI 改文案）时，后果被限制在**顺序排差、多几次 codex 启动**，
而不是「把好账号误判成死的、还告诉调用方没号可用」。

**第一版说「最坏只多一次启动」，这是错的，撤回。** 正确的上界是 **N−1 次多余启动**
（N = 账号数）：顺序完全排反时，前 N−1 个都要撞一次才轮到能用的那个。
而且这个上界**只在前面每一次都是可重试的额度失败时成立**——非额度失败会立即停止（见下）。

### 非额度失败立即停止，以及它的代价

换账号救不了「代码写错了」「brief 有问题」这类失败，只会白烧一轮。所以只有额度失败才换号。

**代价要写明：** 如果排在前面的账号因为非额度原因失败，后面那个本来能用的账号**这一次不会被试到**。
这是刻意选的——自动重跑一个已经真实失败过的任务，比少试一个账号危险得多。调用方看到失败原因后
重跑即可，而那时前一个账号的失败已经记在案。

### 账号局部故障 ≠ 任务失败

`ensure_isolation` 会因为「该账号没有登录态」直接 `reject` 退出 2。在 `auto` 模式下，
这会让**一个账号缺登录态就把整条命令打死**，哪怕别的账号完全可用。

修法是把两类前提分开，**不笼统吞掉所有 `Rejected`**：

| 前提 | 性质 | auto 模式下怎么办 |
|---|---|---|
| 该账号有登录态（`auth_source(account)` 存在） | **账号局部** | **进候选之前就过滤掉**。一个都不剩时 `reject`，并点名每个账号缺的是哪个文件 |
| 共享扫描根 `~/.agents/skills` 为空 | **全局** | 照旧致命。换账号救不了它，而且隔离的前提一旦破，本工具的核心承诺就是空的 |
| `config.toml` 不是软链 | 账号局部 | 照旧致命。这是一条一次性的人工修复（删掉重跑就好），不值得为它增加分支 |

登录态过滤**不违反「状态只排序不拒绝」**：那条约束管的是**额度记录**（一份会过期、会出错的缓存）；
登录态是当场可查的硬前提，没有它那个账号连启动都启动不了。

### 算法

```
候选 = auto ? 有登录态的账号按 (是否已住在该账号, reset_at, 账号名) 升序 : [指定的那个]
        ——候选列表**先去重再定序**，之后不再变动（见「保留名与唯一性」）

「任务还在跑」的入口检查：进循环之前查一次
        ——它问的是「这个任务名此刻有没有活着的 codex」，与试哪个账号无关。
           **这不能替代 run_codex 内部每次启动前的等待**，那一条管的是「上一轮的 writer
           和 codex 是否都排干了」，每次 spawn 都必须做，不许因为刚删过元数据就跳过。

for 第 i 个账号 in 候选:
    ensure_isolation(账号)
    round = run_codex(...)                    # 元数据在这里、spawn 之前落盘
    verdict = judge(round)
    额度失败 = verdict.state == "failed" and 额度谓词(runtime_error_lines(round.text))
    if 额度失败:
        从 **同一个 round.text** 解析恢复时间并落盘   ← 不许另读整份历史日志
        记进「已满」清单（解析不出时间也要记，值为「未知」）
        if auto 且 i 不是最后一个:
            删掉本任务在该 home 的元数据，继续下一个
    if 已满清单 > 1:
        verdict = Verdict("failed", "全部 N 个账号都撞上额度上限", [逐个列出恢复时间])
    打印并返回 EXIT[verdict.state]
```

**恢复时间必须从 `judge` 用的那同一个 `Round.text` 里解析。** 另读整份历史日志会把上一轮、
上一个任务的旧额度错误和旧时间当成本轮事实——这正是 `Round` 这个类型存在的理由。

### 为什么要删元数据，以及删到什么程度

`run_codex` 在 spawn **之前**就把元数据写进了该账号的 home（第 1311 行写、第 1354 行才 `Popen`）。
而 `cmd_run` 有一道护栏：同名任务不许跨账号。不删的话第二次尝试会被自己的护栏挡住。

但**最后一个候选失败时不删**。第一版没写这个限定，审查实测了后果：三个账号全满之后
`status` 列表为空、`status <任务名>` 说「没有这个任务」——任务凭空消失。

**关于「一个任务名在任何时刻只属于一个隔离目录」这个说法：第一版把它当成无条件不变量，
这站不住。** 迁移过程中有一个窗口（删掉旧的、到新的落盘之间，其中还夹着
`_wait_previous_round_ends`），此刻并发的 `status`/`resume`/`stop` 会查不到这个任务。
如实写下来，不假装它不存在。要真正消灭它需要任务名级的互斥覆盖整次重试——
**那是另一件事，本次不做**，因为现有 `write_meta` 的注释已经承认「查完到写完之间有窗口」，
这次没有把那个窗口变得更糟。

### 保留名与候选唯一性

`account_choices()` 返回 `["default"] + 扫描到的目录名`。实测：`~/.codex-accounts/` 下建
`default` 和 `auto` 两个目录，返回的是 `['default', 'acct2', 'auto', 'default']`——
**`default` 出现两次，且两次指向同一个 home**。

后果：同一个 home 被扫两遍，`find_meta` 对同一份元数据数出两份，当场 `reject`
「任务名在多个隔离目录里都有」；而 `auto` 一旦成为 CLI 模式词，名叫 `auto` 的真账号就再也没法
被明确指定。

修法：`account_choices()` 里把 `default` 和 `auto` 两个名字都列为**保留名，扫到就拒跑**并点名
是哪个目录——和现有「目录名含空白或控制字符就拒跑」同一处、同一种处置。不静默去重：
静默去重会让住在那个目录里的任务从 `status` 里消失，正是这个函数的注释反复强调要避免的静默失效。

### `--account` 仍然必填

取值多一个 `auto`。没有任何隐式选中的值。代价是每次调用都要写一遍 `--account auto`，
用户已知情并选择了这个。

## 五、刻意不做

| 不做 | 理由 |
|---|---|
| `status` 增加账号限流行 | 「什么时候能干活」的答案放在失败信息里，那正是需要它的时刻。`status` 的机器可读格式是刻意设计的契约。**但这不能成为「让失败任务查不到」的理由**——所以最后一个候选的元数据必须保留 |
| 新增状态码 / 给 `Verdict` 加字段 | 五态和退出码不变。重试原因由**共用谓词**提供，不解析中文 reason，也不加字段（见第二节的 8ms 权衡） |
| 按套餐档位排序 | 对称且不可测量的偏好，该被剃掉 |
| 预测/跟踪剩余额度 | 当前验证过的接口都不提供。任何基于它的设计都是在猜 |
| 任务名级互斥锁 | 能消灭迁移窗口，但那是既有问题的一个更大范围的修法，不属于本次 |

## 验收判据

**全部是行为判据。** 第一版用过「测试数 ≥ 250 只增不减」，撤回——基线本来就满足它，证明不了
新功能，而且和仓库规范第 7 条「积极删除或合并」直接冲突。

1. **额度判据的正例与负例都要有**
   - 正例：直引号版本、弯引号版本、**以及一份未经我手的真实日志字节**，都判成额度上限
   - 负例：brief 或源码里**提到**这句话、但本轮实际是被打断的，必须判成 `interrupted`（退出 130），
     **不换号、不删元数据**
   - 负例：常量被改成一个过宽的串（如单个字母）时，上面那条负例必须变红
2. **恢复时间**：解析真实消息、四种序数后缀、12AM/12PM、月份乱写、不存在的日期——
   解析不出时不写文件、不影响本轮判据；解析出来的是朴素时间（无 tzinfo）
3. **缓存的失效模式**：文件缺失／坏 JSON／缺键／类型错，读出 `None` 且不崩；写失败不阻断重试；
   临时文件名带 pid，两个并发写者不会把对方的半截内容替换进去
4. **分配与重试**（用假子进程驱动真实 `cmd_run → run_codex → judge`）：
   - 第一个账号额度失败、第二个成功 → 断言实际尝试顺序、brief/effort/skills 逐轮不变、退出码 0
   - 每个候选最多启动一次；强制模式只启动一次
   - 非额度失败 → 立即停止，不试后面的账号
   - 全满 → 退出 1，且 `status <任务名>` **仍然查得到这个任务**，恢复时间未知时如实显示「未知」
   - 缺登录态的账号在 auto 模式下被跳过而不是让整条命令退 2；一个都没有时 `reject` 并点名
5. **保留名与唯一性**：`~/.codex-accounts/default` 或 `auto` 存在时 `account_choices()` 拒跑并点名目录
6. **既有约束不被破坏**：现有的等待、轮次边界、信号相关测试全部保留且全绿
7. **收尾**：`SKILL.md` / `README.md` 与实际 CLI 一致；结论内化进代码注释后，
   删除本 spec 与对应计划文档（仓库规范第 7 条）
