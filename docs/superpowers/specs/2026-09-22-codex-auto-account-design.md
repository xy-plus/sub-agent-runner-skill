# codex-sub-agent 账号自动分配

## 目标

调用方不再需要知道哪个账号还有额度。`--account auto` 让工具自己挑，撞上额度上限就换下一个。

用户原话：「我希望调用这个 skill 的时候，不再有管理账号的麻烦，直接调用就好了。我们这边根据账户的
额度和重置时间，来决定怎么分配账号。」

> **v3（2026-09-22）**。前两版都被审查子代理退回，两次的根问题是同一个：
> **这次改动把一条给人看的解释性判据，升级成了删状态、重跑任务的控制依据。**
> v2 试图靠「只看已分类的错误行」来提高证据可靠性，被证伪——格式分类不等于来源事实。
> v3 换了方向：**不再试图让日志变可信，而是不让日志决定这件事。**

## 一、可观测性决定了方案的形状

| 事实 | 可观测吗 | 怎么测的 |
|---|---|---|
| 账号**还剩多少**额度 | 当前验证过的接口都不提供 | 没有 `codex usage`/`quota`/`limits`/`account` 子命令；`codex doctor` 不报；`auth.json` 里没有 |
| 账号**已经用完了** | 可以，且消息自带恢复时间 | 2026-09-22 实跑一个已限流账号：**退出码 1、耗时 15 秒、消息在 stderr**，内容是 `You’ve hit your usage limit … try again at Sep 26th, 2026 5:47 PM` |

两件配套事实约束了设计：

1. **额度是周级的。** 实测 `acct3` 停到 9/25 17:04、`default` 停到 9/26 17:47，都在 3~4 天后。
   一次撞上限那个账号停好几天——「每次都从头试一遍」的无状态方案代价过高。
2. **恢复时间是错开的。** 所以排序键是恢复时间本身，不是套餐档位（`default`/`acct2` 是 pro、
   `acct3` 是 plus）。先烧大的还是先烧小的，一周总容量不变，对称且不可测量，按奥卡姆剃刀剃掉。

**没有可用的非文本信号。** 实测撞上限的退出码是 1，和普通失败没区别；分流也救不了——
codex 把 header、**prompt 回显**、自己的错误全写在 stderr。

## 二、地基：判据既匹配不上真的，又匹配得上假的

### 匹配不上真的

源码常量是 `"You've hit your usage limit"`（ASCII 直引号 U+0027），codex 输出的是弯引号 U+2019。
27 份日志、54 行额度错误全是弯引号。所以这条特判是**死代码**，`status` 至今把撞上限的任务
报成「报告缺失或为空」。

修法：判据缩短成 `"hit your usage limit"`——**砍掉含标点的那一截**，剩下全是字母和空格。
不是把直引号换成弯引号，那仍然押在一个会变的字符上。

### 匹配得上假的——而且今天真实发生了

v2 以为「只在 `runtime_error_lines()` 的返回值里找」就够了。**不够。**
那个函数逐行 `strip()` 之后只按格式匹配（`^ERROR:` / tracing target / `^Error:`），
**只认格式，不认来源**。brief 里一行缩进的 `    ERROR: ...usage limit` 照样进得去。

不是构造的反例。今天这个项目自己的审查任务就撞上了：

```
plan-review-auto-account  acct2  suspect  3
    ERROR: You’ve hit your usage limit
```

`acct2` **完全正常**（那一轮产出了 19,771 字节的报告）。那些行来自 codex 读取计划文档本身——
日志里能看到它带行号 `cat` 出了计划里含这个字面串的那几行。

**在 v1/v2 的设计下，这一轮如果恰好没产出报告，工具会删掉它的元数据、换账号把整个任务重跑一遍。**

## 三、核心设计：换账号由独立探测决定，不由任务日志决定

> **任务日志只决定「要不要花 15 秒探一下」，不决定「换不换账号」。**

```
任务这一轮失败且没有报告
        │
        ├─ 日志里有额度字样吗？ ──否──→ 就是普通失败，照常返回，不换号
        │         （廉价闸门，误判的代价只是白探一次）
        ↓ 是
   对这个账号做一次独立探测
        │  用我们自己写死的 prompt，不含任何额度字样
        │  ⇒ 它的输出里不可能有被回显进来的假证据
        │
        ├─ 探测说没撞上限 ──→ 那刚才那行是污染。照常返回原判据，不换号
        ↓ 探测说撞上限了
   记下恢复时间（**从探测的输出解析，不从任务日志解析**），换下一个账号
```

| 性质 | 说明 |
|---|---|
| 误判的代价 | 从「删元数据 + 重跑整个任务」降到「白花 15 秒探测一次」 |
| 恢复时间的来源 | 探测的干净输出，不是可能被污染的任务日志 |
| 重跑的安全性 | 探测确认撞上限，意味着那一轮 codex 从未拿到响应、**证明零工作量**，重跑不会产生重复副作用 |
| 探测本身的代价 | 账号真的满了：15 秒、零 token（服务端直接拒）。账号其实没满：会真跑一轮极短的 prompt，消耗几百 token。只在已经失败且日志有额度字样时才发生 |

**探测的 prompt 必须写死在代码里，且不得含任何额度字样。** 这是它全部可信度的来源，
用常量而不是参数——参数就能被调用方污染，那就绕回原点了。

## 四、状态：每个隔离目录一个 `usage_limit.json`

```json
{"reset_at": "2026-09-25T17:04:00", "raw": "Sep 25th, 2026 5:04 PM"}
```

| 决定 | 理由 |
|---|---|
| 放隔离目录 | 限流是**账号**的属性，账号已经有一个家。`ensure_isolation` 的不变量是五个子目录存在、共享扫描根为空、`config.toml` 不是软链、`auth.json` 软链到该账号——**不枚举也不拒绝顶层多余文件**（实测确认） |
| 留 `raw`、不留 `seen_at` | 前者是审计线索，后者没有消费者 |
| 临时文件名**带 pid** | 这个文件是**账号级、跨任务共享**的，同账号上两个任务可能同时写。`write_meta` 的固定临时名安全是因为「一个任务只有一个写者」，**这个前提在这里不成立** |
| 读校验要完整 | 文件缺失、坏 JSON、缺任一键、`raw` 不是字符串、`reset_at` 解析失败、**解析出来带时区**（带时区的值之后和朴素时间比较会抛 `TypeError`）——全部返回 `None` |
| 读失败＝没有记录 | `None` 的含义是「排最前、照样会被试到」，那是安全的一边。反过来会把可用账号锁死且调用方看不出原因 |
| **写失败不许打断重试** | 记录是优化不是前提。调用方必须吞掉写盘异常继续试下一个账号 |
| 不做过期清理 | 排序**不读当前时间**，过期记录不会自动变成「无记录」——它排进「恢复得早的那一批」，批内按先后排，语义依然正确。清理需要读时钟、需要定义「多久算过期」，是纯增实体 |

**时区不编造。** 消息里没有时区，实测也推不出来（恢复时间在 3~4 天后）。存朴素本地时间。
安全性来自下一节：这个值只当排序键。

## 五、分配

### 额度记录只排顺序，不准拒绝

> 「全部账号都撞上额度上限」这个结论永远来自真实尝试，不来自文件。

记录写错时后果限制在**顺序排差、多几次 codex 启动**。上界是 **N−1 次多余启动**（N = 候选数），
且**只在前面每一次都被探测确认为额度失败时成立**——非额度失败会立即停止。

### 登录态是唯一的前置过滤，它不违反上面那条

`ensure_isolation` 会因为该账号没有 `auth.json` 直接 `reject` 退出 2。不过滤的话，
**一个账号缺登录态就会把整条 auto 命令打死**，哪怕别的账号完全可用。

「只排序不拒绝」管的是**额度记录**（一份会过期、会出错的缓存）；登录态是当场可查的硬前提。
两者性质不同。共享扫描根非空是**全局**前提，照旧致命——换账号救不了它。

### 归属迁移要显式做，不能靠排序暗中保证

v2 说「auto 模式下任务原有的账号一定排第一，所以跨账号同名护栏不需要了」。**这不成立**：
如果原账号恰好没有登录态，它会被过滤掉，于是第一个候选是别的账号，而护栏已经被拿掉——
结果是两个隔离目录各有一份元数据，`find_meta` 之后一律退 2。审查实测复现过。

所以迁移写成显式的一步，排在入口检查之后、循环之前：

```
入口检查：任务已有归属且它的 codex 还活着 → 拒跑（查一次，与试哪个账号无关）
          ★ 这不替代 run_codex 内部每次 spawn 前的等待，那一条每轮都必须做
auto 模式：任务已有归属，但那个账号不在候选里（没登录态）
          → 打印一行说明，删掉旧元数据，显式迁移
```

### 算法

```
候选 = auto ? 有登录态的账号按 (是否已住在该账号, reset_at, 账号名) 升序 : [指定的那个]
       候选列表定下来之后不再变动；一个账号只出现一次
auto 且候选为空 → reject，逐个点名每个账号缺的是哪个文件

for 第 i 个账号 in 候选:
    ensure_isolation(账号)
    round = run_codex(...)          # 元数据在这里、spawn 之前落盘
    verdict = judge(round)
    if verdict.state == "failed" 且 日志里有额度字样:
        探测结果 = 独立探测(账号)
        if 探测确认撞上限:
            写 usage_limit.json（时间来自探测输出；**写失败要吞掉异常继续**）
            记进「已满」清单
            if auto 且 i 不是最后一个:
                删掉本任务在该 home 的元数据，继续下一个
    if 本轮被确认为额度失败 且 已满清单长度 == 候选数:
        verdict = Verdict("failed", "全部 N 个账号都撞上额度上限", [逐个列出恢复时间])
    打印并返回 EXIT[verdict.state]
```

**汇总条件必须同时满足两条。** v2 写的是 `if len(exhausted) > 1`，放在 `if limited` 外面，
审查实测：`acct2` 满 → `acct3` 满 → `default` **成功**，最终却报「全部 2 个账号都撞上额度上限」
并退出 1。成功被覆盖成了失败。

**最后一个候选失败时不删元数据。** 删了的话全满之后任务凭空消失——`status` 列表为空、
`status <任务名>` 说「没有这个任务」。审查实测过。

**「一个任务名只属于一个隔离目录」不是无条件不变量。** 迁移过程中有一个窗口
（删掉旧的、到新的落盘之间，中间还夹着 `_wait_previous_round_ends`），此刻并发的
`status`/`resume`/`stop` 查不到这个任务。如实写下来。真正消灭它需要任务名级互斥覆盖整次重试，
**本次不做**——现有 `write_meta` 的注释已经承认存在类似窗口，这次没把它变得更糟。

### 保留名与候选唯一性

实测：`~/.codex-accounts/` 下建 `default` 和 `auto` 两个目录，`account_choices()` 返回
`['default', 'acct2', 'auto', 'default']`——**`default` 出现两次，两次指向同一个 home**，
`find_meta` 会对同一份元数据数出两份并当场误拒。

`default` 和 `auto` 都列为保留名，扫到就拒跑并点名目录——和现有「目录名含空白或控制字符就拒跑」
同一处、同一种处置。**不静默去重**：那会让住在那个目录里的任务从 `status` 消失。

**拒绝半径是整个 CLI**（`account_choices()` 挂在 `build_parser()` 的 `choices=` 上），
所以错误信息里必须给出完整的迁移办法，而不只是「改个名」：目录改名之后，
旧任务仍留在 `.codex-subagent-auto` 里、之后扫描不到，要连隔离目录一起改名。

### `--account` 仍然必填

取值多一个 `auto`。没有任何隐式选中的值。

## 六、刻意不做

| 不做 | 理由 |
|---|---|
| `status` 增加账号限流行 | 「什么时候能干活」的答案在失败信息里，那正是需要它的时刻。`status` 的机器可读格式是刻意设计的契约。**但这不能成为让失败任务查不到的理由**——所以最后一个候选的元数据必须保留 |
| 新增状态码 / 给 `Verdict` 加字段 | 五态和退出码不变 |
| 按套餐档位排序 | 对称且不可测量的偏好 |
| 预测剩余额度 | 当前验证过的接口都不提供 |
| 任务名级互斥锁 | 能消灭迁移窗口，但那是既有问题更大范围的修法 |
| 把额度证据的「来源隔离」做成解析器 | 试过了（v2），证伪了。探测把这件事整个绕开，比解析 prompt 回显区间少一个实体 |

## 验收判据

全部是行为判据。**不设测试数量门槛**——基线本来就满足，证明不了新功能，且与仓库规范第 7 条
「积极删除或合并」冲突。

1. **额度字样的识别**：直引号、弯引号、以及一份**未经我手的真实日志字节**都要认出来；
   常量不含标点
2. **污染不许造成换号**：brief 里含 `    ERROR: …usage limit`（缩进的也算）、
   探测却说账号正常 → **不换号、不删元数据、不写 usage_limit.json**，退出码按原判据
3. **打断优先**：brief 含额度字样 + 真实打断标记 → 退出 130，不换号、不删元数据
4. **探测的输入是写死的**：断言探测用的 prompt 是模块级常量且不含 `usage limit` 字样
5. **恢复时间**：真实消息、四种序数后缀、12AM/12PM、**小时必须在 1–12**（`99:04 PM` 现在会被
   取模成 15:04，要拒掉）、月份乱写、不存在的日期——解析不出就不写文件、不影响本轮判据；
   返回的 `raw` **只含日期时间**，不含 `try again at ` 前缀；时间无 tzinfo
6. **缓存的失效模式**：缺文件／坏 JSON／缺任一键／`raw` 类型错／带时区 → 读出 `None` 不崩；
   **写盘抛异常时重试必须继续，断言第二个账号确实被启动**；临时名带 pid 且
   **真实写入路径确实用了当前 pid**（把 writer 固定成常数 pid 的突变必须被杀死）
7. **分配与重试**（**mock `Popen` 驱动真实 `cmd_run → run_codex → judge`**，不替换 `run_codex`）：
   - 第一个满、第二个成 → 尝试顺序、每轮 brief/effort/**skills 非空集合**逐字不变、退出码 0
   - **满、满、成功 → 退出 0**，不得被汇总成「全部都满」
   - 每个候选最多启动一次；强制模式只启动一次
   - 非额度失败立即停止，且退出码是该失败本身的码
   - 全满 → 退出 1，**`cmd_status` 仍列得出这个任务**，恢复时间未知时如实显示
   - 原归属账号没登录态 → 显式迁移，结束后**只有一份元数据**
   - 所有账号都没登录态 → `reject` 并**逐个点名**（断言每个账号都出现）
8. **保留名**：`default` 或 `auto` 目录存在时拒跑并点名，错误信息含隔离目录的迁移办法
9. **既有测试全绿**：含 `test_codex_sub_agent.py:851` 那条——它拿裸常量当错误行用，
   新判据下要改成真正的错误行 fixture，但它原本钉的断言（真实额度错误优先于打断）必须保留
10. **收尾**：`SKILL.md` / `README.md` 与 CLI 一致（README 里「七种空测试」的说法也要跟着改）；
    结论内化进代码注释后，删除本 spec 与计划文档
