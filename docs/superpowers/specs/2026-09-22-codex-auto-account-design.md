# codex-sub-agent 账号自动分配

## 目标

调用方不再需要知道哪个账号还有额度。`--account auto` 让工具自己挑。

用户原话：「我希望调用这个 skill 的时候，不再有管理账号的麻烦，直接调用就好了。我们这边根据账户的
额度和重置时间，来决定怎么分配账号。」

> **v4（2026-09-22）：去掉轮内自动重试。**
> v1~v3 都在给「撞上限就自动换账号重跑」找安全的做法，v3 为此加了一个独立探测机制。
> 但那整条路建立在我写的一句话上——「撞上限的那一轮 codex 从未拿到响应，证明零工作量」——
> **实测推翻了它**（见第二节）。前提没了，重试就不该做，探测也就不必存在。
> 用户据此重新决定：**只自动挑号，不轮内重试。**

## 一、可观测性决定了方案的形状

| 事实 | 可观测吗 | 怎么测的 |
|---|---|---|
| 账号**还剩多少**额度 | 当前验证过的接口都不提供 | 没有 `codex usage`/`quota`/`limits`/`account` 子命令；`codex doctor` 不报；`auth.json` 里没有 |
| 账号**已经用完了** | 可以，消息自带恢复时间 | 实跑一个已限流账号：退出码 1、15 秒、消息在 stderr |

**额度是周级或 5 小时级的**（两种消息形态见第三节），一次撞上限那个账号停几小时到几天。
**恢复时间是错开的**，所以排序键是恢复时间本身，不是套餐档位——先烧大的还是先烧小的，
总容量不变，对称且不可测量，剃掉。

## 二、为什么不做轮内重试

v1~v3 的安全论证是：撞上限的那一轮 codex 从未拿到响应，零工作量，重跑无副作用。

**实测（269 份现网日志，56 条真·额度错误行）：**

| | |
|---|---|
| 距本轮开头的行数 | 中位 **101**，最小 **41**，最大 **23,630**（1.19 MB） |
| 在轮首 12 行以内的 | **0 / 56** |

**额度永远是在任务跑到一半用完的，一次例外都没有。** 而重跑用的是同一个 `--dir`、
同一份 brief、`--sandbox danger-full-access`——落在一棵已经被改过的树上。

「这一轮到底改没改过文件」这件事**没法可靠地知道**：唯一的线索是日志文本，而日志正是被污染的
那个东西（见第四节）。所以不做轮内重试。

**代价写明：** 后台任务撞上限就停下，需要有人重发命令。但重发是安全的——重发时
`auto` 已经知道这个账号满了，会自动挑别的。**「重试」从工具的一个循环，变成了调用方的一次重发。**

## 三、地基：额度判据

### 修掉「匹配不上真的」

源码常量原本是 `"You've hit your usage limit"`（ASCII 直引号 U+0027），codex 输出弯引号 U+2019。
所以这条特判是**死代码**，`status` 把撞上限的任务报成「报告缺失或为空」。

修法：缩短成 `"hit your usage limit"`——**砍掉含标点的那一截**，剩下全是字母和空格。
不是把直引号换成弯引号，那仍然押在一个会变的字符上。

### 判据只看已分类的错误行

`hit_usage_limit()` 收 `runtime_error_lines()` 的返回值，不对整轮自由文本做裸子串匹配。
这挡不住全部污染（见第四节），但它是免费的收窄，且和本文件 `_ERR_*` 上方那段
「绝不能用裸 grep」的既有规矩一致。

### 打断标记优先于额度字样

打断标记是**本工具自己写的**（`interrupt_codex` 发完 INT 才写），是关于「**我们**做了什么」的
不可伪造证据；额度字样可伪造。两者同时出现，打断赢。

「两者都真」的唯一现实窗口：codex 已把额度错误写进日志、进程还没退时外部信号进来。
亚秒级，且落在安全的一边（130、不删元数据）。

### 两种恢复时间形态

| 形态 | 行 / 文件 | 谁 |
|---|---|---|
| `try again at Sep 25th, 2026 5:04 PM` | 34 / 17 | Pro，周额度 |
| `try again at 11:10 AM`（**只有时刻**） | 22 / 11 | 带 `Upgrade to Pro`，Plus，5 小时档 |
| `You’ve hit your usage limit`（后面什么都没有） | 2 / 1 | **全部出自本项目自己的日志，是污染** |

「只有时刻」占真实消息的 39%。歧义（今天还是明天）只在读到消息那一刻存在，消息说的是
"try again **at**"——未来，所以取 **>= now 的下一个该时刻**。`now` **必填不给缺省**：
这是本功能唯一读时钟的地方，隐式的 `datetime.now()` 会让「今天还是明天」随运行时刻飘。
**排序一次都不读时钟。**

解析不出时间（第三种形态）→ 不写记录，退化成「无记录＝排最前＝下次照样先试它」。

## 四、日志会骗人——但这只影响记录，不影响行为

`runtime_error_lines()` 逐行 `strip()` 后只按格式匹配，**只认格式不认来源**。
brief 原文、codex 读文件的回显、子进程输出都可能匹配上。

**2026-09-22 一天之内自证了四次：**

1. 本项目的 plan 审查任务：`acct2` 完全正常（产出 19,771 字节报告），日志里却有额度错误行
   ——codex 带行号 `cat` 出了计划文档里含这个字面串的行
2. 同一份日志里 `You’ve`（弯，codex 真报的）34 次、`You've`（直）2 次，后者分别来自
   **spec 里解释这个 bug 的那一行**和测试 fixture。老常量**认出 0 条真错误，
   却匹配上了我描述这个 bug 的那句话**
3. 我临时写的账号状态扫描脚本，把计划文档里的测试 fixture `Sep 25th, 2026 5:04 PM`
   当成了 `acct2` 的真实恢复时间
4. 我临时写的「有没有写动作」检测，匹配到的是 brief 和 CLAUDE.md 被回显进日志的文本

**但在 v4 里这件事的爆炸半径只有「记录」。** 误判的后果是给一个健康账号写了条限流记录，
于是它排到后面——**仍然会被选中、仍然会被试**，只是顺序差一点。有界且良性。

这正是去掉重试换来的：同一个不可靠的证据，v3 里驱动「删元数据、换账号重跑整个任务」，
v4 里只驱动「排序时往后挪一格」。**不是把证据变可靠，是把它的权力收小到与其可靠性相称。**

## 五、状态：每个隔离目录一个 `usage_limit.json`

```json
{"reset_at": "2026-09-25T17:04:00", "raw": "Sep 25th, 2026 5:04 PM"}
```

| 决定 | 理由 |
|---|---|
| 放隔离目录 | 限流是**账号**的属性，账号已经有一个家。`ensure_isolation` 不枚举也不拒绝顶层多余文件（实测确认） |
| 留 `raw`、不留 `seen_at` | 前者是审计线索，后者没有消费者 |
| 临时文件名**带 pid** | 这个文件是**账号级、跨任务共享**的，同账号上两个任务可能同时写。`write_meta` 的固定临时名安全是因为「一个任务只有一个写者」，**这个前提在这里不成立** |
| 读校验完整 | 缺文件／坏 JSON／缺任一键／`raw` 不是字符串／`reset_at` 带时区，全部返回 `None`。**带时区那条是会咬人的**：和 `datetime.min` 比会抛 `TypeError`，一个手写坏的文件能把整条 auto 命令打死 |
| 写失败吞掉但**出声** | 记录是优化不是前提。静默失效是这个仓库反复在修的那类病 |
| 不做过期清理 | 排序不读当前时间，过期记录不会自动变成「无记录」——它排进「恢复得早的那一批」，批内按先后排，语义依然正确。清理要读时钟、要定义「多久算过期」，纯增实体 |

时区不编造：消息里没有，实测也推不出来。存朴素本地时间。

## 六、分配

### 排序：纯按恢复时间

```
候选 = 有登录态的账号，按 (reset_at, 账号名) 升序；无记录用 datetime.min 排最前
```

**没有「这个任务已经住在哪」这个键。** v3 有过，那是为重试服务的（沿用旧家、失败再搬走）。
去掉重试之后它会变成陷阱：任务住的那个账号限流了也照样被选中，**每次都失败，永远换不掉**。

**记录只排顺序，不准拒绝。** 「全部账号都满了」这个结论永远来自真实尝试。
唯一的前置过滤是**登录态**——它是当场可查的硬前提，没有 `auth.json` 那个账号连启动都启动不了，
而 `ensure_isolation` 会因此 `reject` 退出 2，**一个账号缺登录态就会把整条 auto 命令打死**。

### 算法

```
入口检查：任务已有归属且它的 codex 还活着 → 拒跑（查一次）
          ★ 不替代 run_codex 内部每次 spawn 前的等待，那一条每轮都必须做

auto  → 候选 = accounts_by_availability(); 空则 reject 并逐个点名缺哪个文件
        选中 = 候选[0]
        任务已有归属且不是选中的那个 → **显式迁移**：打印说明、删掉旧元数据
                                        （旧 home 的报告和日志留在原处，措辞要说清）
强制 → 选中 = 指定的那个；任务已有归属且不是它 → 拒跑（现有护栏原样保留）

跑一轮 → judge
若 failed 且 hit_usage_limit(本轮已分类错误行):
    从**本轮的 round.text** 解析恢复时间并落盘（写失败吞掉但出声）
    在失败信息里告诉调用方：记下了，重跑这条命令会自动换成 <下一个账号>
返回 EXIT[verdict.state]
```

**只跑一轮。** 没有循环、没有 `exhausted` 清单、没有「全满」汇总、没有探测。

### `--account` 仍然必填

取值多一个 `auto`。没有任何隐式选中的值。

### 保留名

`default` 和 `auto` 都是保留名，`~/.codex-accounts/` 下有同名目录就拒跑并点名。
实测不拒的后果：候选返回两个 `default` 且两次指向同一个 home，`find_meta` 对同一份元数据
数出两份；更糟的是 `status`（不带任务名）会把同一个任务列**两行**，当场破坏「一行一任务」
这个机器可读契约。**不静默去重**——那会让住在那个目录里的任务从 `status` 消失。

拒绝半径是整个 CLI（`account_choices()` 挂在 `build_parser()` 的 `choices=` 上），
所以错误信息要给**完整**的迁移办法：光改账号目录名不够，旧任务还留在 `.codex-subagent-auto` 里
之后扫描不到，隔离目录要一起改名。

## 七、刻意不做

| 不做 | 理由 |
|---|---|
| 轮内自动重试 | 见第二节。前提被实测推翻 |
| 独立探测 | 它只为让重试安全而存在。重试没了，它就是零消费者的实体 |
| `status` 增加账号限流行 | 「什么时候能干活」的答案在失败信息里，那正是需要它的时刻；`status` 的机器可读格式是刻意设计的契约 |
| 新增状态码 / 给 `Verdict` 加字段 | 五态和退出码不变 |
| 按套餐档位排序 | 对称且不可测量的偏好 |
| 预测剩余额度 | 当前验证过的接口都不提供 |
| `codex exec --json` | 结构化事件是「文本分不清来源」的根因解法，但换掉主线日志的可读性是真代价，而 v4 里日志的权力已经收小到只影响排序——**不值得为此换掉日志形态**。记在这里，将来若要做更强的判据，从这条起步 |

## 验收判据

1. **额度字样识别**：直引号、弯引号、以及**未经我手的真实日志字节**都要认出来；常量不含标点
2. **打断优先**：brief 含额度字样 + 真实打断标记 → 退出 130，不写 `usage_limit.json`
3. **两种恢复时间形态**都解析得出，用现网真实字节验过；只有时刻的取 >= now 的下一个该时刻，
   跨午夜/跨月/跨年正确；`now` 必填；小时必须 1–12（`99:04 PM` 要拒，不许取模成 15:04）；
   `raw` 只含日期时间，不含 `try again at ` 前缀
4. **缓存失效模式**：缺文件／坏 JSON／缺键／`raw` 类型错／带时区 → `None` 不崩；写失败吞掉但出声
5. **排序**：按 `(reset_at, 账号名)`；**没有「任务住在哪」这个键**；无记录排最前；
   过期记录排在无记录之后（语义正确）；有登录态的账号**一个都不少**
6. **分配**（mock `Popen` 驱动真实 `cmd_run → run_codex → judge`）：
   - `auto` 选中候选[0]，**只启动一次 codex**
   - 撞上限 → 写 `usage_limit.json`；失败信息里点名下次会换成哪个账号
   - 任务原本在别的账号 → 显式迁移，结束后 `all_metas()` **只有一份**；提示措辞不得声称
     旧 home 的报告被删（它没被删）
   - 强制模式：跨账号同名仍然拒跑；撞上限照样记录
   - 缺登录态的账号被跳过；全缺时 `reject` 并**逐个点名**
7. **保留名**：`default` / `auto` 目录存在时拒跑并点名，错误信息含隔离目录的迁移办法
8. **既有测试全绿**
9. **收尾**：`SKILL.md` / `README.md` 与 CLI 一致；结论内化进代码注释后删除本 spec 与计划文档
