# 等的不是「codex 没了」，是「写日志的那个进程走了」

日期：2026-09-20　状态：按用户反馈重写（上一版用日志文本当信道，被否），待审查

判据层级：**三条铁律 > 仓库规范 > 既有文档**。

## 1. 病根

`interrupt-and-resume` 打断当前轮之后要等它真结束才能续跑。现在等的是
**codex 进程从 `/proc` 里消失**。

但真正要知道的是**「还会不会有人往这份日志里写字」**，而那个人是**包装器**，不是 codex：
包装器的 tee 循环读 codex 的 stdout **管道**，循环在**管道 EOF** 时才结束；
而 codex 起的孙进程**继承了这个 stdout**，所以 codex 死了管道不会 EOF。

2026-09-20 实测（孙进程 sleep 3 后再写一行）：

```
codex 进程真正退出于  t=0.04s
tee 循环（管道 EOF）于 t=3.08s
```

**窗口不是几毫秒，是孙进程活多久就多久。** 这期间续跑已经开始、新一轮的分隔符落了下去，
而上一轮的尾巴还在往后追——上一轮丢掉自己的尾巴，新一轮白背上一轮的错误行。

用户能看见的症状：插话之后 `status` 偶尔说「干完了，但日志里有可疑错误」，
而那些错误是**被打断的上一轮**留下的。（承重结论不受影响：打断痕迹在这一切之前就写了。）

## 2. 问题其实很简单，别把它做复杂

要问的就是一句话：**「写日志的那个进程还在不在？」**

本设计的第一版用「包装器写完时往日志追一行收尾标记、等的人去文本匹配那一行」——
**那是在拿给人读的日志当进程间信道，为了一个布尔值去做文本匹配**，而且带着一个洞
（包装器被 `kill -9` 时标记永远不出现，等的人只能一直等到超时）。已否掉。

正确答案是标准做法：**排他文件锁**。

| 谁 | 做什么 |
|---|---|
| `run_codex`（写日志的那个） | 开工时对**日志文件本身**加排他锁，持到进程结束 |
| 想知道它写完没的人 | 试着加同一把锁。拿到 ＝ 它走了；拿不到 ＝ 还在写 |

**关键在于锁是内核释放的，不是程序释放的。** 2026-09-20 实测：

| 情况 | 锁 |
|---|---|
| 写日志的进程活着 | 被持着 |
| 正常退出（孙进程仍在跑） | **释放** |
| **`kill -9`**（孙进程仍在跑） | **释放** |
| 孙进程 | **不继承**（`close_fds` 默认关掉） |

## 3. 这条修法删掉的东西

| 删掉 | 因为 |
|---|---|
| 「PID 会过期、会被系统复用」这个顾虑 | 答案由内核给，不存在过期 |
| 上一版的收尾标记 + 整行正则 + `has_round_end_mark()` | 不需要任何文本 |
| 「包装器被硬杀就永远等不到 → 超时后叫人改用 `resume`」那整条退路 | 洞不存在了 |
| 轮询循环 | 可以直接阻塞等，内核在对方退出的那一刻叫醒你 |

**净减法。** 这是判断这版对不对的一个信号：上一版是往上加东西，这版是拿掉东西。

## 4. 契约

```
wait_for_writer(log_path, timeout) -> bool     # True=写日志的那个已经走了
```

- 锁加在**日志文件本身**，不新建文件——`run_codex` 本来就开着它。
- `run_codex` 拿锁的位置：**打开日志之后、写分隔符之前**。拿不到就说明上一轮还在写，
  那本身就是个应该报出来的错。
- `cmd_interrupt_and_resume` 里 `wait_for_exit` 换成它，**并且不论有没有发过 INT 都要等**
  ——codex 早没了而包装器还在排干，正是本次要修的那种情况。
- 超时仍然保留（防内核层面的意外挂起），但正常路径上等不到超时。

### `find_codex_pid` 不动

它回答的是另一个问题：「codex 本身还在不在」——`stop` 要用它决定发不发信号，
`cmd_interrupt_and_resume` 要用它决定**要不要打断**。这两件事和「日志写完没」是两回事。

## 5. 测试

| 测什么 | 关键点 |
|---|---|
| 还在写时等不到 | 起一个真的持锁进程 → `wait_for_writer` 在超时内返回 False |
| 走了就等到 | 持锁进程退出 → 立即 True |
| **`kill -9` 也等得到** | 硬杀持锁进程 → True（这条是这版相对标记方案的核心优势） |
| **codex 早没了、包装器还在排干时必须继续等** | 本次的回归锁。突变：换回等 PID → 必须红 |
| 孙进程不继承锁 | 持锁进程退出但孙进程仍活 → True |
| `run_codex` 真的拿了锁 | 跑一轮期间外部拿不到锁；跑完能拿到。突变：不拿锁 → 必须红 |
| 上一轮没写完就起新一轮 | `run_codex` 拿不到锁 → 拒绝并说人话 |
| 超时 | 锁一直被持 → 返回 False，调用方拒绝续跑、退出码 2；等待期间 `os.kill` 零调用 |

依赖外部进程的测试**先断言前提成立**（本仓栽过七次）。
