# 等的不是「codex 没了」，是「这一轮的日志写完了」

日期：2026-09-20　状态：待审查

判据层级：**三条铁律 > 仓库规范 > 既有文档**。

## 1. 病根

`interrupt-and-resume` 打断当前轮之后，要等它真的结束才能续跑。现在等的是
**codex 进程从 `/proc` 里消失**（`wait_for_exit`）。

但真正要知道的是**「还会不会有人往这份日志里写字」**，而那个人是**包装器**，不是 codex：

- 包装器的 tee 循环读的是 codex 的 stdout **管道**，循环在**管道 EOF** 时才结束；
- codex 起的孙进程**继承了这个 stdout**，所以 codex 自己死了，管道**不会** EOF。

2026-09-20 实测（孙进程 sleep 3 秒后再写一行）：

```
codex 进程真正退出于  t=0.04s
tee 循环（管道 EOF）于 t=3.08s
```

**窗口不是几毫秒，是孙进程活多久就多久。** 这期间续跑已经开始，新一轮的分隔符写进了日志，
而上一轮的尾巴还在往后追——于是上一轮丢掉自己的尾巴，新一轮白背上一轮的错误行。

用户能看见的症状：插话之后 `status` 偶尔说「干完了，但日志里有可疑错误」，
而那些错误其实是**被打断的上一轮**留下的。

（承重结论不受影响：打断痕迹是在这一切之前写的，所以「被打断 → 接着 resume」始终正确。）

## 2. 这是同一类 bug 的第四层

本仓的轮次边界问题已经修过三层，每层的修法都自带一个没人保证的新前提：

| 层 | 修法 | 新引入的推测 |
|---|---|---|
| 1 | 左边界改成记下字节偏移 | 右边界还在猜 |
| 2 | 右边界改整行匹配 | 整行匹配假设了行首 |
| 3 | 写者前置换行保证行首 | **「写完了没」还在猜** |
| 4 | 本次 | —— |

四层的正解是同一句话：**写者保证，而不是读者猜。**

## 3. 修法

**包装器在自己的 tee 循环结束后，往日志写一行收尾标记。** 想知道「写完了没」的人
等那一行，不再去猜 PID。

```
ROUND_END_MARK = "----- codex-agent 本轮日志到此为止 -----"
wait_for_round_end(log_path, timeout, poll_interval) -> bool
```

- 写在 `run_codex` 的 **`finally`** 里——异常路径也必须写，否则等待方会永远等下去。
- 整行匹配（`_END_LINE`），**写者前置 `\n` 保证落在行首**——第 3 层的教训直接适用。
- `cmd_interrupt_and_resume` 里 `wait_for_exit` 换成它，**并且不论有没有发过 INT 都要等**：
  codex 早就没了而包装器还在排干，正是本次要修的那种情况。

### 为什么不是别的办法

| 方案 | 否掉的理由 |
|---|---|
| 等「日志 N 秒不长」 | 那是**启发式**，还是读者在猜。本仓刚把三层猜测逐层拆掉，不该在第四层引入第四个猜 |
| 去 `/proc` 找包装器进程 | 需要一套新的进程识别（按 argv 找 `--task <名>`），比标记重得多，且和「不存 PID」那条既有决定拧着 |
| 把标记写在单独的文件里 | 多一个实体。日志已经是那个「谁写谁负责」的地方，标记进日志还顺带让人一眼看出这一轮到哪结束 |

### 包装器被硬杀怎么办

`kill -9` 之后标记永远不会出现，等待方会一直等到超时。**超时的处置是拒绝并说人话**：
告诉调用方改用 `resume`——`resume` 不等这个标记，它只拒绝「codex 还在跑」，而那时 codex 确实没了。

这是刻意的取舍：**宁可在罕见情况下多要一条命令，也不在常见情况下猜错。**

## 4. 对既有判据的影响

- `runtime_error_lines`：收尾标记不匹配任何错误形式，不影响。
- `judge` 的报告预览：读的是报告不是日志，不影响。
- `read_round` / `read_last_round`：标记是本轮的最后一行，落在区间内，不影响右端截断。
- `INTERRUPT_MARK` 与 `ROUND_END_MARK` 前缀相同（`----- codex-agent `），
  但两条整行正则互不匹配——**这正是当初把两类标记都改成整行匹配换来的**。

## 5. 测试

| 测什么 | 关键点 |
|---|---|
| 正常收尾写标记 | 跑完一轮，最后一行是标记且**落在行首** |
| **异常路径也写** | tee 循环里抛异常 → 标记仍在（突变：把 `finally` 改成正常路径写 → 必须红） |
| 等的是标记不是 PID | **codex 的 PID 早已消失、标记还没出现** → 必须继续等（这是本次的回归锁，突变：换回等 PID → 必须红） |
| 没发 INT 也要等 | 任务已不在跑但包装器仍在排干 → 仍然等 |
| 超时 | 标记始终不出现 → 拒绝、退出码 2、**消息里点名改用 `resume`**；且等待期间 `os.kill` 零调用 |
| 行首 | 上一块输出无换行结尾时，标记仍被 `_END_LINE` 认出 |
| 两类标记互不误认 | 日志里有收尾标记时 `has_interrupt_mark` 为 False，反之亦然 |

依赖外部进程的测试**先断言前提成立**——本仓栽过七次（含「把参数改必填让 `assertRaises` 变同义反复」「为防病而写的测试自己是空的」）。

## 6. 非目标

- 不动 `resume`：它不等这个标记，语义不变。
- 不动 `stop`：它只发信号，不等。
- 不改 `judge` 的任何判据。
