## 1. 两个独立的改动

审查指出：把它们混成一件事，会让 B 的正当性被 A 顺带带过去。拆开各自验收。

| | 是什么 | 为什么成立 |
|---|---|---|
| **改动 A** | 判据说真话：轮次边界记下来而不是推测、打断必留痕、`interrupted` 是第五态 | 修的是**现在就在说谎**的三件事，与新命令无关，实测证据充分 |
| **改动 B** | 新命令 `interrupt-and-resume` | 把**等待循环**从调用方手里收回。这是它唯一独有的收益 |

B 依赖 A（没有 A，B 续跑之后被打断那一轮仍会发出假的 `failed` 通知），所以一起交付，
但分开论证、分开验收。

## 2. 改动 A-1：轮次边界必须记下来，不能推测

### 病根

`judge` 靠 `current_round()` 按**最后一个** `ROUND_MARK` 往回切，来划定「本轮」。
这等于说：**一轮的边界是从日志里猜出来的，而日志是多个进程共写的。**

后果（审查确定性复现）：`interrupt-and-resume` 一确认 codex 退出就调 `run_codex`，
往同一个日志追加新的 `ROUND_MARK`；而被打断那一轮的 `run` 包装器此刻正要跑判据。
谁先谁后**没有任何保证**——包装器晚一步，`INTERRUPT_MARK` 就被切到本轮之外：

```
A) 只有打断标记时       → 本轮被 INT 打断，上下文保留——接着 resume 即可
B) 新分隔符落地之后     → 报告缺失或为空＝没正常收尾        ← 同一份日志
```

实测两者落在同一秒内。判据成本还随日志增长（0.83MB 时 7.6ms），长任务上天平继续朝
竞争方倾斜——**而长任务正是最该打断、上下文最值钱的场景**。

### 修法：谁开的轮，谁记下自己的起点

`run_codex` 写完分隔符时就知道自己的起始偏移（`log.tell()`）。把它显式带下去：

```
run_codex(...) -> int                      # 返回本轮在日志中的起始偏移
read_round(log_path, start_offset) -> str  # [start_offset, 之后第一个 ROUND_MARK)
read_last_round(log_path) -> str           # 外部观察者用（status）
judge(report_path, round_text, pid) -> Verdict
```

- **本轮的拥有者**（`cmd_run` / `_resume_with`）用 `read_round` + 自己那个偏移。
  偏移是 codex 还没起跑之前拿到的，**后来的任何一轮都不可能把它致盲**。
- **外部观察者**（`cmd_status`）用 `read_last_round`——它本来就只能看最后一轮，诚实。

区间右端截到「起点之后的第一个 `ROUND_MARK`」，所以后一轮的内容也不会被吞进来。

**这不是给 P1 打补丁，是把「边界」从推测变成事实。** 「后来的一轮把前一轮判瞎」
这一整类问题结构上消失。

## 3. 改动 A-2：发 INT 与留痕焊成一个动作

`cmd_stop` 用 `os.kill(pid, SIGINT)` 直接打给 codex，而写痕迹的 `note_interrupt`
**只在包装器自己的信号处理器里被调用**。于是 `stop` 这条路上痕迹永远不写。实测：

```
stop 打印:  已向 rv-probe1 (pid=602545) 发 SIGINT，上下文保留，可 resume
包装器收尾: failed —— 报告缺失或为空＝没正常收尾        ← 退出码 1
日志里 INTERRUPT_MARK 计数: 0
```

```
interrupt_codex(pid, log_path) -> None
```

先发信号，成功了再留痕（没送出去就不该留假痕迹）。三条路全部走它：
`forward_as_sigint`、`cmd_stop`、新命令。

**返回值刻意不给。** 审查指出「返回 bool 谁检查」是新的滥用面；而三个调用点没有一个
需要区分——「它本来就没在跑」这件事由调用方在**调用之前**用 `find_codex_pid` 判，
那才是判它的地方。

**不违反「存活和可观测是两件事」**：原文那句约束的是**失效域独立**——可观测的失效
不许拖垮存活。这里降级方向正是如此：`note_interrupt` 吞掉 `OSError`，留痕写不进去
就算了，INT 已经发出去了。而「发出 INT」和「记下它发生过」不是两个域，
**是同一事件的两面**——拆开就是一句「记得也写一下标记」的软约定，已经漏过一次。

## 4. 改动 A-3：`interrupted` 是第五态

### 为什么 reason 不够，必须动退出码

harness 的完成通知**只搬退出码，不搬 stdout**。所以 `judge` 的 reason 字符串再准确
也到不了做决定的那一方；**能到的只有那个数字**。而在这唯一到得了的通道上，
`interrupted` 和 `failed` 目前是同一个值，处置却相反。

损失可量化：审查的探针被打断时已烧掉 **28,107 tokens**，退出码 1 会让照 SKILL.md
契约做决定的 agent 从头重跑，那 28k 连同保住的上下文一起扔掉。

### 它推翻的是一个写明了理由的旧决定

`test_codex_agent.py:274` 写着 `assertEqual(v.state, "failed")  # 产物确实没出来，状态不变`。

**正面回应**：产物没出来是事实，但状态回答的不是「产物出来没有」，而是
**「接下来该干什么」**——五个状态都是按这个轴分的。

| 状态 | 接下来该干什么 |
|---|---|
| `success` 0 | 不用干什么 |
| `running` 4 | 等 |
| `interrupted` 5 | **接着 resume** |
| `suspect` 3 | 去看一眼 |
| `failed` 1 | 查原因，**重跑** |

改动时旧理由和推翻它的理由都留在注释里。

### 严重度位置：在 `running` **之后**

```
_STATES = (("success", 0), ("running", 4), ("interrupted", 5), ("suspect", 3), ("failed", 1))
```

顺序即严重度（越靠后越该拦住调用方）。**`interrupted` 必须排在 `running` 之后**：
在跑的任务会自己好，**被打断的永远不会自己好**——它在等人动手。
`status` 列一批任务时若被 `running` 盖住，调用方会去「等」一个永远不会自己好的东西。
（初稿排反了，审查纠正。）

`_worse("running", "interrupted") == "interrupted"` 要单独钉死一条测试——
少钉一对，`_SEVERITY` 就能被悄悄重排。

### 打断与错误行共存时

被 INT 打断几乎必然在日志里留下
`ERROR codex_core::session: failed to record rollout items: thread … not found`，
而 `codex_core::session` 刻意不在良性白名单里。

**优先级：状态取 `interrupted`（处置是 resume），错误行照常进 `detail`。**
不动白名单——那条 ERROR 在非打断场景下仍然该被看见。

## 5. 改动 B：`interrupt-and-resume`

### 它唯一独有的收益（审查把其余两条都归了别处）

初稿声称「手工连敲 stop+resume 会撞写锁，且报错和 SIGTERM 锁死一模一样、判不出来」——
**实测证伪**：`stop` 之后 0.164 秒 resume，拿到的是护栏的干净拒绝（exit 2），
不是 `thread-store conflict`。`cmd_resume` 早就装了那道闸。

真实缺口小得多，但确实存在：**护栏只会拒绝，不会替你等。**
调用方拿到 exit 2 之后得自己写重试循环，而那个循环——间隔多少、上界多少、
超时了怎么办——是彻头彻尾的软约定，每个调用方现编一遍，编错了没人告诉他。

**收走这个循环，就是这条命令存在的全部理由。** 它够不够格？够：
这正是铁律 2——把只有一种正确写法的东西编进代码，而不是留给每个调用方去背。

### 契约

```
codex-agent interrupt-and-resume <任务名> --brief msg.md --effort {low|medium|high|xhigh|max}
```

参数规则与 `resume` **逐条一致**（任务名走 `type=task_name`、`--brief` 只收文件路径、
`--effort` 必填无默认、不收 `--account`）。同一个工具里 prompt 只有一种传法。

### 执行顺序：**所有拒绝都发生在发信号之前**

这是硬约束，不是排版顺序：

```
1. 任务存在？          不存在 → 拒绝
2. 元数据有 session id？ 没有   → 拒绝
3. 工作目录还在？       不在   → 拒绝
4. --brief 是文件？     不是   → 拒绝
   ────────── 以上四道闸全过，才允许动手 ──────────
5. 查真实 PID
   ├ 没在跑 → 打印「本来就没在跑，直接续跑」
   └ 在跑   → 本轮已有打断痕迹？
              ├ 有 → 只等，不再发信号（见下）
              └ 无 → interrupt_codex → 等待退出
6. 续跑
```

**为什么顺序是硬约束**：INT 发出去就收不回来。先打断、再发现没 session id，
那一轮白毁**且拿不回来**（没 session id 就没法 resume）。这个窗口真实可达——
`session_id` 要等 codex 第一块输出才写进元数据，代码注释自己记着「实测父进程
4.06 秒才看到 banner」，而任务刚起那几秒正是最可能被打断的时候（刚发现 brief 写错）。

测试要有突变：把 session-id 检查挪到 INT 之后 → 必须红。

### 重试不许发第二发 INT

超时的处置是「稍后重试」，而重试就是再跑一遍这条命令 → 又一次 `interrupt_codex`
→ **第二发 INT**。很多 CLI 把第二发 Ctrl-C 当强退；codex 是不是这样**完全没验过**。
如果是，就可能走成不干净退出 → 写锁不释放 → 上下文全丢，正是本命令要防的事。

「永不升级信号」在单次调用内成立，**被重试路径绕过去了**。

**修法用已有的痕迹，不加新实体**：发信号之前先看本轮日志有没有 `INTERRUPT_MARK`，
有就说明这一轮已经打断过——**只等，不发**。

### 等待退出

```
wait_for_exit(report_path, timeout, poll_interval) -> bool
INTERRUPT_EXIT_TIMEOUT = 60      # 秒，上界不是等待时长
INTERRUPT_POLL_INTERVAL = 0.2
```

轮询真实 PID（与 `status` 同一套：扫 `/proc` + argv 精确元素比对 + `comm` + 同用户）。
**只轮询，不发任何信号。** 超时 → 拒绝续跑，退出码 `2`，告诉调用方稍后重试。
绝不升级：SIGTERM 会让会话永久锁死，不可逆。

**60 秒的实测锚点**（审查实测，codex 0.154.0，effort low，`sleep` 工具调用执行中被打断）：
INT → PID 消失分别是 **1.854 秒**和 **0.964 秒**。60 秒是 30~60 倍余量——
够大到不会误杀正常收尾，够小到卡住时调用方不会被无限期挂着。
**两个数字写进常量旁的注释**，否则下一个人会随手改它。

必须是**模块级常量**（不是函数默认参数）：测试要把它 patch 成 0.3 秒；
也正合仓库规范「不要默认缺省值」。

### 不提供的旋钮

`--now`、`--wait`、`--force`、`--timeout`、`--message`、`--account` —— 没有第二种正确行为。

### 退出码

`0` success、`1` failed、`2` 护栏拒绝、`3` suspect、`4` running、`5` interrupted。
命令的退出码是**续跑那一轮的判据结论**。

## 6. SKILL.md

加第四条命令，并写明**只有人/模型才能决定的那件事**：

- 插话＝**打断当前轮**。要不要为此打断，**看信息本身值不值**——工具不替你判：
  这个判断要知道「这条信息值多少」和「在途工作损失多少」，后者在 codex 里根本不可观测。
- 已做的部分**留在上下文里不会白做**（0.154.0 实测：打断后 resume，追问「被打断前你
  成功创建了哪几个文件」，codex 答「s1.txt」，磁盘上确实只有 s1.txt）。
- 退出码表加 `5 interrupted`，并明确一句：**看数字，不看词**。
  harness 的完成通知对任何非零码都写 `failed with exit code N`，
  「failed」这个词消不掉，能区分的只有那个数字。

不写进 SKILL.md 的：信号怎么发、窗口怎么等、痕迹怎么留、边界怎么划——都是代码的事。
仓库有一条真测试钉着「已由代码保证的约束不许在文档里重说」。

## 7. 测试

| 测什么 | 关键点 |
|---|---|
| **轮次边界不被后来的轮次致盲** | 拥有者拿着偏移判据；在它判之前往日志追加新 `ROUND_MARK` + 新内容 → 结论必须不变（这是 P1 的回归锁） |
| 区间右端截断 | 后一轮的内容不许被吞进前一轮 |
| 三条路都留痕 | 突变：任一调用点改回裸 `os.kill` → 必须红 |
| 五态绝对值 | `assertEqual(EXIT, {...})` 五个数字钉死；`USAGE_ERROR` 不在其中；`_SEVERITY` 顺序钉死；**`_worse("running","interrupted") == "interrupted"` 单独钉一条** |
| 打断+错误共存 | 状态取 `interrupted`，错误行仍进 detail |
| 额度上限／写锁仍是 `failed` | 它们 resume 救不回来，不许被第五态顺手吃掉 |
| **拒绝必须在发信号之前** | 突变：把 session-id 检查挪到 INT 之后 → 必须红 |
| **重试不发第二发 INT** | 本轮日志已有 `INTERRUPT_MARK` → `os.kill` 必须没被调用 |
| 五种入场情况 | 任务不存在／没 session id／目录没了／brief 不是文件／没在跑，各自走对分支 |
| 等待退出 | 超时返回 False；等待期间 `os.kill` 零调用；超时是上界不是等待时长 |
| 参数一致性 | 与 `resume` 同一张断言表；六个旋钮逐个被拒 |
| SKILL.md | 泄漏测试仍绿（新增文字不许出现信号／窗口／痕迹这类机制词） |

依赖外部进程的测试**先断言前提成立**——空测试比没测试更糟，这个仓库栽过四次。
凡「断言常量等于那个常量自己」的写法一律视为空测试。

## 8. 非目标

- 不做收件箱：`codex exec` 结构上没有。实测 `codex queue` 对它完全无效——
  跑时不收、resume 也不收，而且**静默成功**（exit 0），比不能用更危险。
- 不换传输层：app-server／daemon 能做到工具边界插话（socket 路径由 `CODEX_HOME` 派生，
  私有 daemon 可行，隔离不会破），但要押在标着 `[experimental]` 的协议上，
  而这个仓库刚被 codex 的版本漂移教训过三次（`--sandbox`、`--color`、`queue`）。
- 不做「等本轮自然结束再送达」：粒度不对（长任务上等于返工），且要引入 pending 队列这个新实体。
