## 1. 问题的本质

原始文档「它正在跑，而我有话要说」一节说得很清楚：

> `codex exec` **没有收件箱**——没有任何办法往正在跑的那一轮里塞消息。给它新信息
> 只有一条路：**结束这一轮，然后 `resume`**。要不要为此打断它，看信息本身。

用户已确认这条路够用，**不换传输层**（app-server／daemon 方案风险太大，且要押在标着
`[experimental]` 的协议上）。所以要解决的不是「有没有别的路」，而是**这条已知的路，
手工走会踩两个静默的坑**：

### 坑一：竞态（原始文档第 157-161 行专门记过）

> 一个线程只许一个写者，所以对**还在跑**的会话 resume，报的错和 SIGTERM 锁死一模一样。
> 2026-09-17 两次 resume 都栽在这里……**resume 之前先用真实 PID 确认真的退出了**：
> 这两种情况的处置完全相反，一个是等它跑完，一个是弃了重开。

`stop` 只是把 SIGINT 发出去就返回了，codex 要过一会儿才真的退出。手工连着敲
`stop` 再 `resume`，几乎必然撞上这个窗口。**而两种病因的报错一模一样**，撞上了也判不出来。

### 坑二：通知说谎（2026-09-19 实测）

`cmd_stop` 用 `os.kill(pid, SIGINT)` **直接打给 codex**，而写打断标记的 `note_interrupt`
**只在包装器自己的信号处理器 `forward_as_sigint` 里被调用**。于是 `stop` 这条路上标记
永远不会写。实测三者当场互相矛盾：

| 谁说的 | 说了什么 |
|---|---|
| `codex-agent stop` | 「上下文保留，可 resume」 |
| `codex-agent status` | `failed —— 报告缺失或为空＝没正常收尾`，退出码 1 |
| harness 完成通知 | **failed with exit code 1** |

整套设计最核心的收益——「完成通知里直接带成败结论」——**在这条路上是假的**。
交给别的 agent 用，它看到 `failed` 会从头重跑，把好好保着的上下文扔掉。

`note_interrupt` 函数本身是对的（O_APPEND + 单次 `os.write`，跨进程原子），
它的 docstring 里甚至原样记着这个症状。**病在调用点缺了一个，不在函数。**

### 坑二只修一半是不够的：退出码也在说谎

`judge` 认出 `INTERRUPT_MARK` 之后返回的仍然是 `Verdict("failed", ...)`，
于是退出码是 `1`。修好标记只让**文字**变对，**退出码还在说「我失败了，重跑吧」**——
而 `SKILL.md` 把退出码印成了对外契约，agent 正是照它做决定的。

按四态自己的组织原则想一遍：这四个状态回答的是「**接下来该干什么**」。

| 状态 | 该干什么 |
|---|---|
| `success` | 不用干什么 |
| `suspect` | 去看一眼 |
| `failed` | 查原因，**重跑** |
| `running` | 等 |
| **被打断** | **`resume`** ←和以上四个都不同 |

所以它是**第五个状态**，不是 `failed` 下的一个理由：

```
EXIT = {"success": 0, "failed": 1, "suspect": 3, "running": 4, "interrupted": 5}
_SEVERITY = ["success", "interrupted", "running", "suspect", "failed"]
```

严重度排在 `running` 之前：被打断的任务是**等着你续跑**，比「还在跑」更不该拦住调用方，
但比 `success` 更需要你做点什么。

**不加这一态的代价是具体的**：agent 拿到 `failed` 会从头重跑，把保着的上下文和已花的
token 一起扔掉。这不是洁癖，是一次真实的浪费。

### 所以这个命令不是语法糖

它把两个**已知会踩、且踩了判不出来**的坑焊死在一个动作里。这是铁律 2
（把约束做进设计本身）的直接应用，不是为了少敲一条命令。

## 2. 原始文档的相关主张，逐条过铁律

不是「有没有对上」，而是「这条主张经不经得起铁律，以及我们据此该怎么做」。

| 原始文档的主张 | 过不过铁律 | 本设计怎么做 |
|---|---|---|
| 「`codex exec` 没有收件箱」 | **过**（第一性原理）。实测坐实：`codex queue` 对 exec 会话完全无效，跑时不收、resume 也不收，且**静默**成功 | 不假装有。命令名里的 `interrupt` 就是在说「只能打断」 |
| 「resume 之前先用真实 PID 确认真的退出了」 | **过**（铁律 2）。两种病因报错一模一样而处置相反，判不出来就会做反 | 编进命令，不可跳过——这正是本命令存在的头号理由 |
| 「永远不写裸 `kill`，只写 `kill -INT`」 | **过**（铁律 2）。SIGTERM 的后果不可逆 | 只发 INT；**超时也绝不升级** |
| 「要不要为此打断它，**看信息本身**」 | **过**（铁律 2，但要看怎么实现）。这是个**价值判断**（这条信息值不值当前这一轮），工具没有信息去替调用方做；**但工具必须让代价可见**，否则判断就是瞎判 | 判断权留在调用方；命令名把代价写在脸上；不提供任何替调用方决定的旋钮 |
| 「存活和可观测是两件事，不能用同一个手段解决」 | **过，但它讲的不是这件事**。原文指的是**两个独立的失效域**（工作进程 vs 通知器——通知器死了，工作一秒都没受影响）。而「发出 INT」和「记下它发生过」不是两个域，**是同一个事件的两面** | §4 把两者焊成一个动作。降级方向仍然正确：先发信号，留痕写不进去就算了（保上下文优先于留痕）——这恰恰是在贯彻原文那句的精神，不是违反 |
| 「**exit 1 ≠ 失败**」 | **过**（第一性原理）：退出码不可信，判据只看产物和日志 | 不动。但见 §1「退出码也在说谎」——判据自己的结论也必须诚实 |

**反向检查**（比「有没有丢」更该花时间）：原始文档里有没有哪条**本身就违反铁律**、
而我们照抄了下来？本设计范围内找到一条——

> 原文把「给它新信息」整段写成了**操作指南**（「结束这一轮，然后 resume」），
> 于是每次都靠调用方照着念对。这是典型的软约定，违反铁律 2。
> 上一轮重做 CLI 时把绝大多数软约定编成了代码，**唯独这一段漏了**——
> `stop` 和 `resume` 两条命令都在，但「两者之间必须确认退出」这个约束仍然只写在文档里。
> 本设计就是在补这一条。

## 3. 命令契约

```
codex-agent interrupt-and-resume <任务名> --brief msg.md --effort {low|medium|high|xhigh|max}
```

参数规则与 `resume` **完全一致**（任务名走 `type=task_name` 把关、`--brief` 只收文件路径、
`--effort` 必填无默认）。理由：同一个工具里 prompt 只有一种传法、难度只有一种给法，
不开第二个家。

### 三种入场情况都要吃

调用方**无法可靠知道**自己处在哪一种——查完到动手之间，任务可能刚好跑完。
所以这条命令必须三种都处理，并**如实打印走了哪条路**：

| 情况 | 行为 |
|---|---|
| 还在跑 | 发 INT + 留痕（原子动作）→ 轮询真实 PID 直到确认退出 → resume |
| 已经结束 | 直接 resume，打印「本来就没在跑，直接续跑」 |
| 元数据里没有 session id | **拒绝**（没法 resume，收了也送不出去） |
| 工作目录不在了 | **拒绝**（与 `resume` 同一道闸） |

### 等待退出

- 轮询真实 PID（`find_codex_pid`，与 `status` 同一套：扫 `/proc` + argv 精确元素比对 +
  `comm` + 同用户）。
- **永不升级信号。** 超时仍未退出 → **拒绝 resume**，打印「还在收尾，稍后重试」，
  退出码 `2`（护栏拒绝）。硬来一次就永久锁死，而那是不可逆的。
- 超时值：`INTERRUPT_EXIT_TIMEOUT = 60`（秒）。它是**上界不是等待时长**——正常情况下
  codex 收到 INT 后几秒内退出，轮询一确认就往下走。

### 不提供的旋钮

`--now`、`--wait`、`--force`、`--timeout`、`--message` —— **没有第二种正确行为**。
每一个旋钮都是一个让调用方做错的机会。

### 退出码

`0` success、`1` failed、`2` 护栏拒绝、`3` suspect、`4` running、**`5` interrupted**（新增，见 §1）。
命令的退出码是**续跑那一轮的判据结论**（与 `resume` 一致）。

## 4. 同一改动里修掉的 bug

把「发 INT」和「留痕」焊成一个不可分的函数，**两条路都必须走它**：

```
interrupt_codex(pid, log_path) -> bool      # 发 INT；成功则写 INTERRUPT_MARK
```

| 调用方 | 现状 | 改后 |
|---|---|---|
| `forward_as_sigint`（包装器被信号打中） | 分两步做对了 | 走 `interrupt_codex` |
| `cmd_stop`（主动停） | **只发信号，没留痕** | 走 `interrupt_codex` |
| `cmd_interrupt_and_resume`（新增） | — | 走 `interrupt_codex` |

顺序是「先发信号，成功了再留痕」：信号没发出去（进程已退出）就不该留下假痕迹。

**这不是新增实体，是收口**：`note_interrupt` 和 `os.kill(SIGINT)` 本来就是一件事的两半，
拆开放就会漏——已经漏了一次。

## 5. 测试

| 测什么 | 关键点 |
|---|---|
| 三条路都留痕 | 突变：任一调用点改回裸 `os.kill` → 必须红 |
| `stop` 之后判据说什么 | 构造「有 INTERRUPT_MARK、无报告」的日志，断言 `judge` 的 **state 是 `interrupted`**（不是 `failed`），且退出码是 `5`（不是 `1`） |
| 五态的绝对值 | `assertEqual(EXIT, {...})` 把五个数字钉死；断言 `USAGE_ERROR`(2) 不在其中；断言 `_SEVERITY` 恰好覆盖五态（教训：派生出来的键集两边一起动＝空测试，这个仓库栽过） |
| 三种入场情况 | 在跑 / 已结束 / 没 session id，各自走对分支且打印对 |
| 等待退出 | 进程迟迟不退 → 超时后**拒绝 resume**、退出码 2、**且没有发出第二个信号**（突变：加一发 TERM → 必须红） |
| 参数一致性 | 与 `resume` 同一张断言表（`type=task_name`、`--brief` 必填、`--effort` 必填且五档） |
| 不提供的旋钮 | `--now --wait --force --timeout --message` 逐个被拒 |

依赖外部进程的测试**先断言前提成立**（空测试比没测试更糟——这个仓库栽过四次）。

## 6. SKILL.md

加这条命令，并写明**只有人/模型才能决定的那件事**：

- 插话会**截断当前轮**——要不要为此打断，看信息本身值不值（原始文档的原话）。
- 已做的部分**留在上下文里，不会白做**（2026-09-19 在 codex 0.154.0 上真机验过：
  追问「被打断前你成功创建了哪几个文件」，codex 自己答得出）。

不写进 SKILL.md 的：竞态怎么避、信号怎么发、标记怎么留——这些是代码的事。
SKILL.md 有一条真测试钉着「已由代码保证的约束不许在文档里重说」。

## 7. 非目标

- 不做收件箱（`codex exec` 结构上没有，实测 `codex queue` 对它完全无效且**静默**）。
- 不换传输层（app-server／daemon 能做到工具边界插话，但要押在 `[experimental]` 协议上，
  且这个仓库刚被 codex 的版本漂移教训过三次）。
- 不做「等本轮自然结束再送达」——粒度不对（长任务上等于返工），且要引入 pending 队列这个新实体。
